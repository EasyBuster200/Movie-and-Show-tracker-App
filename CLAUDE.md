# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A TV Time–style movie/show tracker: browse trending content, save it to lists, track what you've watched (per-episode for shows), rate things, and mark favorites. Runs as a fully local, offline-first Android app (via Capacitor) with per-device "profiles" instead of server accounts — there is no backend. All movie/show metadata comes live from TMDB, called directly from the device using each profile's own TMDB API key.

This is a standalone repo, split off from [Movie-and-Show-tracker-Website](https://github.com/EasyBuster200/Movie-and-Show-tracker-Website) (a separate repo, not a branch of this one) at the commit that rebuilt the original server-backed multi-user website into this local-first app. Full history from before the split — including the original Express/SQLite server-backed version — is preserved in this repo's own git log; that other repo is the actively maintained website version if you need to compare current behavior against it.

## Commands

```bash
npm install       # install dependencies
npm run sync       # npx cap sync android — copies public/ into the Android project
npm run open:android  # npx cap open android — opens the project in Android Studio
```

There is no build step, bundler, or lint config for the web layer — `public/` is plain HTML/CSS/JS loaded directly via `<script>` tags, and Capacitor just wraps it in a WebView (`android/app/src/main/assets/public/` is a synced copy, gitignored, regenerated by `npm run sync`). `npm test` is an unconfigured placeholder (`exit 1`); there is no test suite in this repo.

No `.env`/server-side secrets are needed — each profile supplies its own TMDB API key through the UI (profile-picker.html), stored in `localStorage`.

**Capacitor version note:** pinned to Capacitor 6 (not the latest major) deliberately, for Node 18 compatibility and to pair with Gradle/AGP 8.2.1, built with JDK 17 — JDK 21 predates that AGP pairing's support window. Don't bump `@capacitor/*` without checking this still holds.

## Architecture

**Folder layout:** `public/` (the whole app, loaded into Capacitor's WebView — `styles/` and `scripts/` subfolders, HTML pages at its root), `android/` (the Capacitor-generated native wrapper — mostly generated/boilerplate; `android/app/src/main/AndroidManifest.xml` and `MainActivity.java` are the two files with actual customization, the latter for native back-button handling). `docs/icons/` holds source Material Symbols SVGs used as copy-paste reference for the inline `<svg>` icons scattered through the HTML — not loaded by the app itself, safe to ignore when tracing runtime behavior.

**No backend — a fetch shim replaces the server.** `public/scripts/localApi.js` monkey-patches `window.fetch` and intercepts every `fetch('/api/...')` call the app already makes, so none of the ~49 existing call sites across the app needed to change when the server was removed. It must be the **first** script tag on every page (before `profiles.js`/`auth.js`), so the patch is installed before any page-load-time fetch fires. Two kinds of routes:
- `/api/tmdb/*` — passed straight through to `https://api.themoviedb.org/3/*`, injecting the active profile's own API key as a bearer token (TMDB sends `access-control-allow-origin: *`, so this works from a WebView/browser with no server in between).
- Everything else (`/api/lists/*`, `/api/watched/*`, `/api/ratings/*`, `/api/favorites/*`, `/api/stats`, `/api/recommendations/*`) — handled locally via `route(method, pattern, handler)`/`matchPath()`/`dispatchLocalApi()`, reading/writing the active profile's IndexedDB. Response shapes are identical to the old server API, so `media.js`, `detail.js`, etc. don't know the difference.

**Every actual TMDB network call funnels through two chokepoints** (`handleTmdbPassthrough` for the `/api/tmdb/*` route, `fetchLocalTmdb` for the local routes' own server-side-style enrichment) — fixing something at either point automatically covers every caller, without touching individual routes/pages:
- `queueTmdbRequest` caps real concurrent requests at `TMDB_MAX_CONCURRENT` (20) and gives every request a `TMDB_TIMEOUT_MS` (10s) timeout. Without this, a page that enriches many items at once (Profile's Watched/Favorites sections especially, one TMDB request per item) fires dozens of simultaneous requests, which is slow enough on a phone's real network to look stuck and/or trips TMDB's abuse-rate limiting.
- `fetchLocalTmdb` retries transient failures (429/5xx/timeout, not 404/401) up to `TMDB_MAX_RETRIES` times with a short backoff — previously any transient failure permanently fell back to a blank "Unknown" card (no poster/title/rating) with no retry.
- `inFlightTmdbRequests` shares one in-flight promise across simultaneous callers requesting the exact same path (e.g. `/api/stats` and `/api/watched/movies/details` both wanting the same just-watched movie's `/movie/{id}` at once) instead of each firing its own request.
- `/movie/{id}` and `/tv/{id}` responses specifically (not sub-resources like season data, which needs to stay fresh for new-episode detection) are cached in IndexedDB's `tmdb_cache` store for `TMDB_DETAIL_CACHE_TTL_MS` (7 days) — a movie's runtime or a show's episode count barely ever changes, so once fetched once it's an instant local read on every subsequent lookup, across routes and across page loads, instead of a repeat network round trip.
- `stripAdultItems` filters TMDB's `adult: true`-flagged results out of every `results`/`parts` array (search, discover, trending, recommendations, collection parts) — that flag marks actual pornographic content specifically, not general R-rated mainstream movies/shows, so this doesn't affect legitimate mature content. Deliberately not applied to unrelated arrays like `credits.cast`, where a person object's own `adult` field means something different (their own known-for work) and stripping them would incorrectly drop real cast/crew credits.

**Preview sections cap how much they enrich, not just how much they render.** Profile's Watched/Favorites rows and `shows.js`'s Keep Watching row only ever display a fixed number of items (`WATCHED_PREVIEW_LIMIT`/`KEEP_WATCHING_PREVIEW_LIMIT`, both 20), but naively fetching the full list and truncating client-side still means enriching (one TMDB request each) a profile's *entire* watched/favorites history just to show 20 of them. `/api/watched/movies/details`, `/api/watched/shows`, `/api/favorites/movies`, and `/api/favorites/tv` instead accept an optional `?limit=` that slices the raw rows down *before* enriching (`applyLimit` helper) — the preview pages request `limit + 1` (one extra, so they can still tell whether to show a "view all" tile without knowing the exact total), while `media-list.html`'s "see all" page calls the same endpoints with no `limit`, since it needs the true full list. `/api/stats` is deliberately never limited this way, since it needs accurate totals (e.g. total watch time) across everything, not a sample.

**Local profiles replace server accounts.** `public/scripts/profiles.js` is a small registry in `localStorage` (`tvtc_profiles` key: `[{id, displayName, tmdbApiKey, createdAt}]`, `tvtc_active_profile_id` key: which one is active) — this registry only holds identity, not app data. `public/scripts/auth.js` keeps its old function names (`getCurrentUser`, `requireLogin`, `logout`) so every existing call site (`bookmarks.js`, `detail.js`, `lists.js`, `media.js`, `profile.js`, `media-list.js`) is unchanged; only what backs them did — `getCurrentUser()` now resolves to the active local profile, `requireLogin()` redirects to `profile-picker.html` (not `login.html`, which no longer exists) if none is active. `public/index.html` is the real entry point (`webDir` in `capacitor.config.json`): it redirects to `main.html` or `profile-picker.html` depending on whether a profile is active.

**Each profile gets its own IndexedDB database**, not one shared database with a profile-id column: `public/scripts/localDb.js` opens `tvtc-profile-{profileId}`, object stores mirroring the old `server/schema.sql` tables minus the `user_id` column (the whole database *is* one profile's data) with JS-camelCase field names. This is deliberate: it keeps each profile's data trivially exportable/deletable as one unit (`indexedDB.deleteDatabase(...)` in `profiles.js`'s `deleteProfile`) and keeps the privacy blast radius of a bug contained to one profile rather than every profile sharing one store.

**TMDB API key handling:** entered once per profile on `profile-picker.html` (required field, create or edit), stored in plaintext in `localStorage` — acceptable for a single-device offline app, but worth remembering if adding any profile-sharing/sync feature later. Only presence is validated at entry time, not that the key actually works against TMDB — a bad key surfaces as a generic "Failed to load…" wherever it's used, not a specific "check your API key" message.

**Backup/restore** (`public/scripts/backup.js`) exports a profile's full IndexedDB + its registry entry as a JSON file (`profile.html`'s "Export Backup" button) and imports one back into a new profile (`profile-picker.html`'s "Import Backup" button) — the only way profile data survives a device switch or reinstall. Branches on `window.Capacitor.isNativePlatform()` to use the native Share sheet on Android vs. a plain blob download on the web. Vendored Capacitor Filesystem/Share plugins live as plain `<script>` tags in `public/scripts/vendor/` (no bundler in this project, so they can't be pulled in as npm imports the normal way).

**Frontend has no bundler, so shared code is shared `<script>` includes, and load order matters.** The working convention is `localDb.js` → `localApi.js` → `profiles.js` → `auth.js` → `media.js` → (`search.js` if present) → page-specific script (`app.js`, `bookmarks.js`, `lists.js`, `profile.js`, `detail.js`, `movies.js`, `shows.js`, `search-results.js`, `media-list.js`). `profile-picker.html` is the one page that doesn't follow this — it has no sidebar, so it only loads `localDb.js` → `profiles.js` → `backup.js` → `profile-picker.js`. `media.js` is the de facto shared component library:
- `buildCard(item)` builds the poster card DOM used everywhere content is listed, wiring in click-through to `detail.html?type=&id=`.
- `attachStandardActions(card, item, context, opts)` is the standard entry point every page calls to wire up the save/favorite/watched buttons on a card — don't reimplement these per page.
- `fetchStandardActionContext()` batch-fetches the current profile's watched-movie ids and favorite ids once per page load, so individual card buttons don't each fire their own request.
- `renderPagination(container, currentPage, totalPages, onPageChange)` is the shared windowed Prev/1…/current±2/…/Last/Next widget used by `search-results.js` and the genre-filtered browse grids on `movies.js`/`shows.js`.
- `attachLoadMoreRow(container, fetchPage, renderItem, opts)` appends a card-sized "Load More" tile to a `.media-container` row that fetches and appends the next TMDB page on click (`fetchPage(page)` must resolve to `{results, total_pages}`; `renderItem(raw)` builds a card or returns falsy to skip that result). Used by `app.js`'s trending rows and `movies.js`/`shows.js`'s popular/recommended rows. If `renderItem` filters out some results, a single call keeps pulling subsequent pages on its own (up to `MAX_PAGES_PER_LOAD`) until it's accumulated close to a full page's worth or run out of pages — otherwise a heavily-filtered row (see the Coming Soon note below) would look sparse or empty until the user clicked "Load More" themselves.
- `renderSearchResultRows(resultsEl, rawResults, onSelect)` is the shared poster+title+meta search-row renderer used by `search.js`'s typeahead dropdown and `lists.js`'s quick-add card (`onSelect` differs per caller — navigate to the detail page vs. add to the list).
- `moreBtnContentHtml(label)` builds the icon+label markup shared by `attachLoadMoreRow`'s button and the plain `<a class="more-btn">` "View all" links `profile.js`/`shows.js` append when a preview row has more items than it shows (card-sized tile, not the small dot it used to be — sized and styled to look like one more slot in the row rather than a separate, oddly-proportioned control).

Adding a new page that lists movies/shows should reuse `buildCard`/`attachStandardActions`, not duplicate card-rendering logic.

**Card action layout:** the save/favorite/watched buttons live as an absolutely-positioned overlay on the poster image (`card.overlayActionsEl`), pinned to fixed corners via `.card-action-tr/-bl/-br` (eye=watched top-right, heart=favorite bottom-left, bookmark=save bottom-right) — not in the footer below the title. Lists/Bookmarks' list-removal button (`attachRemoveButton`) reuses the same overlay rather than a separate footer row, taking the one remaining unused corner (`.card-action-tl`), since it isn't part of `attachStandardActions` and only applies on list-management pages.

**Every card-shaped element derives its size from one set of CSS custom properties** (`--card-width`, `--card-poster-ratio`, `--card-info-height`, defined on `:root` in `style.css`) instead of hardcoding its own numbers — `.card`, `.media-grid`'s columns, and the Lists "add item"/"load more" tiles (`.add-item-card`, `.more-card`) all compute their size from these. This was a deliberate fix for a real bug: `.add-item-card`'s height used to be a hardcoded pixel value tuned only for one card size, so when `--card-width` needed to change between a desktop and mobile breakpoint (there's no longer a desktop layout at all — see the mobile-only note further down) it silently went out of sync and, combined with `.media-container`'s flex default `align-items: stretch`, stretched every real card in that row to match its oversized neighbor. `.media-container`/`.media-grid` now also set `align-items: flex-start`/`start` explicitly so a taller sibling can never do that again regardless of how its height is computed.

**Watched tracking has two different shapes on purpose.** Movies are a single boolean (`watched_movies` store). TV is tracked per episode (`watched_episodes`, one row per show/season/episode) because per-episode progress is the core feature — there's no cached progress counter; "X/Y watched" is always computed live by combining the local watched count with TMDB's `number_of_episodes`. `detail.js`'s season accordion lazy-loads episode lists per season and, when you mark an episode watched, offers a "catch up" prompt to bulk-mark every earlier unwatched episode across all prior seasons too.

**Bookmarks are still stored as a list under the hood** — the one `lists` row per profile with `isDefault: true`, auto-created when a profile's database is first opened — but is treated as a separate concept in the UI: `lists.js`'s `fetchLists()` filters out the default list, so it never appears on `lists.html`, and `bookmarks.html` is its own dedicated page (with movie/show items split into two separate `.media-container`s). It still shows up as a checkable option in the "Save to a list" popover (`media.js`'s `attachSaveButton`, which hits `GET /api/lists` directly and isn't filtered) since that's still how items get added to it. Don't add a parallel bookmarks store/API if extending this — the split is presentation-only.

**Ratings:** stored as an integer 1–10 (`ratings` store, keyed by `{mediaType}:{tmdbId}`), but only ever displayed as a 5-star half-increment widget on the detail page (`star value = rating / 2`). Cards elsewhere (Home/Bookmarks/Lists/Profile) do not show a rating control at all — that was deliberately removed in favor of detail-page-only rating.

**`detail.html`/`detail.js` is the single content page for both movies and shows**, distinguished by a `?type=movie|tv&id=<tmdbId>` query string — there's no separate movie-detail vs show-detail template. TV-specific sections (seasons/episodes) are simply hidden/skipped when `type=movie`.

**There's a de facto "standard item shape" used everywhere media is passed around client-side**: `{ tmdbId, mediaType, title, year, releaseDate, posterPath, voteAverage }`. It's produced independently by `localApi.js`'s `fetchLocalMediaSummary` (mirroring the old `server/tmdbClient.js`'s `fetchMediaSummary`), and by `media.js`'s `normalizeTmdbTrendingItem` and `detail.js`'s `toStandardItem` — three separate implementations of the same contract rather than one shared definition. If you touch one, check the others stay in sync. `releaseDate` specifically is what powers **unreleased-content gating**: `media.js`'s `attachWatchedButton` and `detail.js`'s `buildEpisodeCard` each independently disable the watched-toggle (and, for episodes, swap in "Coming Soon" placeholders) when `releaseDate`/`air_date` is missing or in the future — same pattern, implemented twice, not shared. Two more variants of the same idea: `movies.js`'s Coming Soon row passes `attachLoadMoreRow` a `filterItem` that drops results whose `release_date` has already passed (TMDB's `/movie/upcoming` endpoint includes titles that, by the time it's fetched, already released), and `detail.js`'s season accordion disables (not just labels) a season's header button when `episode_count === 0`, so tapping a Coming Soon season can't get stuck on a permanent "Loading episodes…" for a season with nothing to load.

**Recommendations** (`localApi.js`'s `GET /api/recommendations/:mediaType` route) are seed-based, not a raw TMDB passthrough: it seeds from the profile's 5 most-recently-touched watched/list items, fetches TMDB's `/recommendations` for each seed, merges and ranks by match count then popularity, and excludes anything already watched/listed or a seed itself. The seeding/ranking (the expensive part — one TMDB request per seed) only depends on watched/list state as of when it first runs, so the ranked pool is cached in memory per `mediaType` for the rest of the page's session (`recommendationPoolCache`) rather than redone on every paginated request; a fresh page load always starts over. `?page=` slices `REC_PAGE_SIZE` (20) items at a time off that cached pool for `attachLoadMoreRow`. Powers the "Recommended" rows on `movies.html`/`shows.html`.

**"Keep Watching" and "Airing Soon" rely on a bounded new-episode heuristic**, not a webhook/polling system: `localApi.js`'s `computeNewEpisodeSeasons` only checks seasons at or above the profile's highest-watched season, comparing episode air dates against `lastWatchedAt`. This feeds the "new episode" dot on `shows.js`'s Keep Watching cards, the "New" labels in `detail.js`'s season accordion, and (via `GET /api/watched/shows/upcoming`) the Home page's "Airing Soon" row, which distinguishes a logged-out empty state from a logged-in-but-nothing-upcoming one via a 401 check.

Also: `movies.js`/`shows.js`'s "Popular" rows use `discover/movie|tv?with_origin_country=<region>` (region guessed from `navigator.language` via `media.js`'s `getUserRegion()`) to bias results toward the user's locale.

**This is a phone/tablet app, not a website — there is no desktop layout.** `#sidebar` is always a fixed bottom tab bar (icon-only, no text labels, no collapse/expand toggle); there's no `@media` breakpoint switching to a wider-screen layout, since one never renders at desktop widths. If you're touching sidebar/layout CSS, there's only ever the one definition to update, not a desktop version plus a mobile override.

**TMDB attribution** (per their API Terms of Use) lives on `profile-picker.html` — the bottom tab bar is only 60px tall, with no room for a logo and a sentence of credit text, so it isn't shown there at all.

## Known gaps

- **No automated tests**, despite `localApi.js` re-implementing nontrivial business logic (recommendations ranking, new-episode heuristic, stats aggregation) that used to live server-side — nothing catches drift from the original behavior it's meant to mirror.
- The old server-backed website's data (from before this repo's rebuild) has no migration path into a local profile's IndexedDB — it's a different storage shape entirely. The server-backed version itself is preserved in this repo's git history (before the local-first rebuild commit) and is also the current state of the separate [Movie-and-Show-tracker-Website](https://github.com/EasyBuster200/Movie-and-Show-tracker-Website) repo.
