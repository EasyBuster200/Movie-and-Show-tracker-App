# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Watchlog** (formerly TVTimeClone) is a TV Time–style movie/show tracker: browse trending content, save it to lists, track what you've watched (per-episode for shows), rate things, and mark favorites. Runs as a fully local, offline-first Android app (via Capacitor) with per-device "profiles" instead of server accounts — there is no backend. All movie/show metadata comes live from TMDB, called directly from the device using each profile's own TMDB API key.

This is a standalone repo, split off from [Movie-and-Show-tracker-Website](https://github.com/EasyBuster200/Movie-and-Show-tracker-Website) (a separate repo, not a branch of this one) at the commit that rebuilt the original server-backed multi-user website into this local-first app. Full history from before the split — including the original Express/SQLite server-backed version — is preserved in this repo's own git log; that other repo is the actively maintained website version if you need to compare current behavior against it.

## Commands

```bash
npm install       # install dependencies
npm run sync       # npx cap sync android — copies public/ into the Android project
npm run open:android  # npx cap open android — opens the project in Android Studio
npm test          # node --test tests/ — runs the localApi.js/standardItem.js unit tests
```

There is no build step, bundler, or lint config for the web layer — `public/` is plain HTML/CSS/JS loaded directly via `<script>` tags, and Capacitor just wraps it in a WebView (`android/app/src/main/assets/public/` is a synced copy, gitignored, regenerated by `npm run sync`). `npm test` runs the Node test suite in `tests/` (see Testing below).

No `.env`/server-side secrets are needed — each profile supplies its own TMDB API key through the UI (profile-picker.html), stored in `localStorage`.

**Capacitor version note:** pinned to Capacitor 6 (not the latest major) deliberately, for Node 18 compatibility and to pair with Gradle/AGP 8.2.1, built with JDK 17 — JDK 21 predates that AGP pairing's support window. Don't bump `@capacitor/*` without checking this still holds.

## Architecture

**Folder layout:** `public/` (the whole app, loaded into Capacitor's WebView — `styles/` and `scripts/` subfolders, HTML pages at its root), `android/` (the Capacitor-generated native wrapper — mostly generated/boilerplate; `android/app/src/main/AndroidManifest.xml` and `MainActivity.java` are the two files with actual customization, the latter for native back-button handling). `docs/icons/` holds source Material Symbols SVGs used as copy-paste reference for the inline `<svg>` icons scattered through the HTML — not loaded by the app itself, safe to ignore when tracing runtime behavior — plus `watchlog-launcher.svg`, the source artwork for the app icon.

**Name, IDs and app icon.** The display name is **Watchlog**: `capacitor.config.json`'s `appName`, `android/app/src/main/res/values/strings.xml` (`app_name`/`title_activity_main`), page text and README. Some identifiers deliberately still say `tvtimeclone`, and must not be renamed. The Android application id `com.tvtimeclone.app` (`appId`, `strings.xml`'s `package_name`/`custom_url_scheme`, the Java package): changing it makes Android treat the build as a different app, so installs no longer update in place and data is lost without a backup restore. The backup format id (`app: 'tvtimeclone'` in `backup.js`): every existing backup file carries it. The launcher icon (episodes as bars, the latest one ticked) is an adaptive icon: `res/mipmap-anydpi-v26/ic_launcher{,_round}.xml` → `res/drawable/ic_launcher_foreground.xml` (a vector, scaled to stay inside the 66dp safe zone) on `@color/ic_launcher_background` (`#5E63FF`, the app's accent). Pre-Android-8 devices use the `res/mipmap-*/ic_launcher{,_round}.png` files, rendered from the same shapes. Changing the artwork means updating the SVG, the vector and those PNGs together.

**No backend — a fetch shim replaces the server.** `public/scripts/localApi.js` monkey-patches `window.fetch` and intercepts every `fetch('/api/...')` call the app already makes, so none of the ~49 existing call sites across the app needed to change when the server was removed. It must be the **first** script tag on every page (before `profiles.js`/`auth.js`), so the patch is installed before any page-load-time fetch fires. Two kinds of routes:
- `/api/tmdb/*` — passed straight through to `https://api.themoviedb.org/3/*`, injecting the active profile's own API key as a bearer token (TMDB sends `access-control-allow-origin: *`, so this works from a WebView/browser with no server in between).
- Everything else (`/api/lists/*`, `/api/watched/*`, `/api/ratings/*`, `/api/favorites/*`, `/api/stats`, `/api/recommendations/*`) — handled locally via `route(method, pattern, handler)`/`matchPath()`/`dispatchLocalApi()`, reading/writing the active profile's IndexedDB. Response shapes are identical to the old server API, so `media.js`, `detail.js`, etc. don't know the difference.

**Every actual TMDB network call funnels through two chokepoints** (`handleTmdbPassthrough` for the `/api/tmdb/*` route, `fetchLocalTmdb` for the local routes' own server-side-style enrichment) — fixing something at either point automatically covers every caller, without touching individual routes/pages:
- `queueTmdbRequest` caps real concurrent requests at `TMDB_MAX_CONCURRENT` (20) and gives every request a `TMDB_TIMEOUT_MS` (10s) timeout. Without this, a page that enriches many items at once (Profile's Watched/Favorites sections especially, one TMDB request per item) fires dozens of simultaneous requests, which is slow enough on a phone's real network to look stuck and/or trips TMDB's abuse-rate limiting.
- `fetchLocalTmdb` retries transient failures (429/5xx/timeout, not 404/401) up to `TMDB_MAX_RETRIES` times with a short backoff — previously any transient failure permanently fell back to a blank "Unknown" card (no poster/title/rating) with no retry.
- `inFlightTmdbRequests` shares one in-flight promise across simultaneous callers requesting the exact same path (e.g. `/api/stats` and `/api/watched/movies/details` both wanting the same just-watched movie's `/movie/{id}` at once) instead of each firing its own request.
- `/movie/{id}` and `/tv/{id}` responses specifically (not sub-resources like season data, which needs to stay fresh for new-episode detection) are cached in IndexedDB's `tmdb_cache` store for `TMDB_DETAIL_CACHE_TTL_MS` (7 days) — a movie's runtime or a show's episode count barely ever changes, so once fetched once it's an instant local read on every subsequent lookup, across routes and across page loads, instead of a repeat network round trip.
- `stripAdultItems` filters TMDB's `adult: true`-flagged results out of every `results`/`parts` array (search, discover, trending, recommendations, collection parts) — that flag marks actual pornographic content specifically, not general R-rated mainstream movies/shows, so this doesn't affect legitimate mature content. `cast`/`crew` arrays are filtered only for entries that carry a `media_type`, meaning a person's `/combined_credits` (real movie/show objects with a real adult flag). They're left alone on a movie/show's own `credits`, where each entry is a person whose `adult` field means something different (their own known-for work) and stripping them would incorrectly drop real cast/crew credits.

**Preview sections cap how much they enrich, not just how much they render.** Profile's Watched/Favorites rows and `shows.js`'s Keep Watching row only ever display a fixed number of items (`WATCHED_PREVIEW_LIMIT`/`KEEP_WATCHING_PREVIEW_LIMIT`, both 8 — smaller than the 20 the TMDB-list-backed rows show, since on a cold cache each visible item here can cost its own TMDB round trip), but naively fetching the full list and truncating client-side still means enriching a profile's *entire* watched/favorites history just to show 8 of them. `/api/watched/movies/details`, `/api/watched/shows`, `/api/favorites/movies`, and `/api/favorites/tv` instead accept an optional `?limit=` that slices the raw rows down *before* enriching (`applyLimit` helper). Profile's four sections request exactly `?limit=8` and always show a "View All" tile once a section has any items, while `media-list.html`'s "see all" page calls the same endpoints with no `limit`, since it needs the true full list. Keep Watching is the exception: it fetches `/api/watched/shows?includeNewEpisodes=true` unlimited and only caps what it *renders*, since it has to check every tracked show's progress before it knows which ones are in progress. `/api/stats` is deliberately never limited either, since it needs accurate totals (e.g. total watch time) across everything, not a sample.

**Watched movies and favorites store their own display fields (denormalized at write time).** When a card's watched/favorite button fires, the client already holds the item's standard shape, so `media.js` sends `pickSummaryFields(item)` (title/year/releaseDate/posterPath/voteAverage) in the POST body and `localApi.js` writes them onto the `watched_movies`/`favorites` row. Reading those lists back (`summaryFromRowOrFetch`) is then a pure IndexedDB read with zero TMDB calls. Rows without them (written before this existed, or by the since-removed TV Time importer, which POSTed with no body) fall back to one live fetch and get backfilled. A failed fetch's "Unknown" placeholder is deliberately *not* persisted, so it stays retryable. Watched *shows* aren't denormalized this way: they need a live `/tv/{id}` anyway for episode count/progress, so it would save nothing.

**Skeleton loading:** `media.js`'s `buildSkeletonCard()`/`renderSkeletonRow(container, count)` render shimmering placeholder cards using the real `.card` markup, so nothing reflows when real cards replace them. `attachLoadMoreRow` shows them on its first load only. Every row that waits on a network fetch uses them (Trending, Popular, Coming Soon, Recommended, Keep Watching, Airing Soon, genre browse grids, search results, media-list, Profile's Watched Shows), and a new network-backed row should too.

**Local profiles replace server accounts.** `public/scripts/profiles.js` is a small registry in `localStorage` (`tvtc_profiles` key: `[{id, displayName, tmdbApiKey, createdAt}]`, `tvtc_active_profile_id` key: which one is active) — this registry only holds identity, not app data. `public/scripts/auth.js` keeps its old function names (`getCurrentUser`, `requireLogin`, `logout`) so every existing call site (`bookmarks.js`, `detail.js`, `lists.js`, `media.js`, `profile.js`, `media-list.js`) is unchanged; only what backs them did — `getCurrentUser()` now resolves to the active local profile, `requireLogin()` redirects to `profile-picker.html` (not `login.html`, which no longer exists) if none is active. `public/index.html` is the real entry point (`webDir` in `capacitor.config.json`): it redirects to `main.html` or `profile-picker.html` depending on whether a profile is active.

**Each profile gets its own IndexedDB database**, not one shared database with a profile-id column: `public/scripts/localDb.js` opens `tvtc-profile-{profileId}`, object stores mirroring the old `server/schema.sql` tables minus the `user_id` column (the whole database *is* one profile's data) with JS-camelCase field names. This is deliberate: it keeps each profile's data trivially exportable/deletable as one unit (`indexedDB.deleteDatabase(...)` in `profiles.js`'s `deleteProfile`) and keeps the privacy blast radius of a bug contained to one profile rather than every profile sharing one store.

**TMDB API key handling:** entered once per profile on `profile-picker.html` (create, edit, or when restoring a backup), stored in plaintext in `localStorage`. That's acceptable for a single-device offline app (it's inside the app's own sandbox), but worth remembering if adding any profile-sharing/sync feature later. The "key" is TMDB's long **API Read Access Token**, sent as a bearer token; the short 32-character v3 "API Key" doesn't work that way. `profiles.js`'s `validateTmdbApiKey()` checks it against TMDB's `/authentication` before saving (only when the key is new or changed) and returns a specific message for a rejected token, a short v3 key pasted by mistake, or no network.

**Backup/restore** (`public/scripts/backup.js`) exports a profile's full IndexedDB data (not `tmdb_cache`) as a JSON file and restores one into a **new** profile, never overwriting an existing one. Backups **never contain the TMDB key** (format `backupVersion: 2`): the files end up in shared places (public Documents, Drive, email), and the key is free to re-obtain. Restoring on `profile-picker.html` opens the profile form in restore mode, asking for a key, validating it, then calling `restoreBackup()`. Restoring from `profile.html`'s "Import Backup" reuses the current profile's key. Old `backupVersion: 1` files did embed the key; they still restore, and `legacyBackupApiKey()` offers that key as a prefill. Manual export ("Export Backup") branches on `isNativeApp()`: the native Share sheet on Android, a plain blob download on the web. Vendored Capacitor plugins (Filesystem, Share, LocalNotifications) live as plain `<script>` tags in `public/scripts/vendor/`, copied from each package's `dist/plugin.js`, since there's no bundler to import them.

**Weekly auto-backup** (`public/scripts/autoBackup.js`, Android only). There's no background job: a few seconds after any page loads, `runAutoBackups()` checks each profile on the device, and for any whose last auto-backup is 7+ days old, writes the same backup JSON to public `Documents/Watchlog/watchlog-<name>-<YYYY-MM-DD>.json`. That folder survives uninstalling the app; IndexedDB doesn't. One file per profile is kept: the new one is written **first**, then the previous one is deleted, so a failed write never leaves zero backups. Android 11+ lets the app write and delete its *own* files there without a storage permission (the Filesystem plugin skips the permission check on API 30+), but not files a previous install created. A failed delete is recorded in `undeleted`, retried on the next run, and shown on the Profile page. State is per profile in localStorage `tvtc_auto_backup` (`{ path, savedAt, undeleted, lastError }`). The Profile menu has "Back Up Now" (`force: true`), plus a status line.

**New-episode notifications** (`public/scripts/notifications.js`, Android only, `@capacitor/local-notifications`). There's no server or push: on page load (throttled to every 6 h per profile, or immediately after a profile switch or a settings toggle), `refreshEpisodeNotifications()` takes `GET /api/watched/shows/upcoming` for the **active** profile and schedules one local notification per show, at `EPISODE_NOTIFY_HOUR` (18:00) local time on its air date. Notification id = the show's TMDB id, and all pending ones are cancelled and rescheduled on each run. Android fires them with the app closed, and the plugin restores them after a reboot. Only each show's *next* episode is known, so the one after it is scheduled on a later app open. Tapping a notification opens `detail.html?type=tv&id=`: every page registers the listener, and the plugin holds the event until one exists. Permission (Android 13+) is requested on the first run; if refused, nothing is scheduled and the app doesn't re-prompt. The on/off switch (localStorage `tvtc_notifications_enabled`) is in the Profile menu. `profile-picker.html` loads it only to clear notifications when no profile is active. The status-bar icon is `android/app/src/main/res/drawable/ic_stat_tvtc.xml`, configured in `capacitor.config.json`'s `LocalNotifications.smallIcon`. Because `/tv/{id}` responses are cached for 7 days, `localApi.js`'s `isTmdbDetailCacheEntryFresh` treats a cached show whose `next_episode_to_air` date has passed as expired, so Airing Soon and notifications learn about the following episode right away.

**Frontend has no bundler, so shared code is shared `<script>` includes, and load order matters.** The working convention is `standardItem.js` → `localDb.js` → `localApi.js` → `profiles.js` → `auth.js` → `media.js` → (`search.js` if present) → page-specific script (`app.js`, `bookmarks.js`, `lists.js`, `profile.js`, `detail.js`, `movies.js`, `shows.js`, `search-results.js`, `media-list.js`, `person.js`). `standardItem.js` goes first because both `localApi.js` and `media.js` use it. It makes no fetches, so it doesn't break the rule that `localApi.js` patches fetch before anything fetches. Every sidebar page also loads the vendored Capacitor scripts (`vendor/capacitor.js`, `capacitor-filesystem.js`, `capacitor-local-notifications.js`, plus `capacitor-share.js` on `profile.html`) as plain non-deferred tags before everything else, and `backup.js` → `autoBackup.js` → `notifications.js` right after `profiles.js`. On the web these load harmlessly, and `isNativeApp()`/`notificationsSupported()` keep them inert. `profile-picker.html` is the one page that doesn't follow this. It has no sidebar, so it only loads `vendor/capacitor.js` + `capacitor-local-notifications.js` → `localDb.js` → `profiles.js` → `notifications.js` → `backup.js` → `profile-picker.js`. `media.js` is the de facto shared component library:
- `buildCard(item)` builds the poster card DOM used everywhere content is listed, wiring in click-through to `detail.html?type=&id=`.
- `attachStandardActions(card, item, context, opts)` is the standard entry point every page calls to wire up the save/favorite/watched buttons on a card — don't reimplement these per page.
- `fetchStandardActionContext()` batch-fetches the current profile's watched-movie ids and favorite ids once per page load, so individual card buttons don't each fire their own request.
- `renderPagination(container, currentPage, totalPages, onPageChange)` is the shared Prev / "Page X of Y" / Next widget used by `search-results.js`, the genre-filtered browse grids on `movies.js`/`shows.js`, and `person.js`'s filmography. It's always exactly three elements, so it fits one phone-width line regardless of page count (the older windowed page-jump version could wrap).
- `attachLoadMoreRow(container, fetchPage, renderItem, opts)` appends a card-sized "Load More" tile to a `.media-container` row that fetches and appends the next TMDB page on click (`fetchPage(page)` must resolve to `{results, total_pages}`; `renderItem(raw)` builds a card or returns falsy to skip that result). Used by `app.js`'s trending rows and `movies.js`/`shows.js`'s popular/recommended rows. If `renderItem` filters out some results, a single call keeps pulling subsequent pages on its own (up to `MAX_PAGES_PER_LOAD`) until it's accumulated close to a full page's worth or run out of pages — otherwise a heavily-filtered row (see the Coming Soon note below) would look sparse or empty until the user clicked "Load More" themselves.
- `renderSearchResultRows(resultsEl, rawResults, onSelect, { includePersons })` is the shared poster+title+meta search-row renderer used by `search.js`'s typeahead dropdown (with `includePersons: true`) and `lists.js`'s quick-add card (movie/show only, since a list can't hold a person). `onSelect` differs per caller: navigate vs. add to the list.
- `normalizeTmdbPerson(raw)`/`personUrl(item)`/`buildPersonCard(person)` are the person (actor/crew) counterparts. A person is deliberately *not* forced into the standard item shape: it has no releaseDate/voteAverage, and its image is a profile photo, not a poster.
- `moreBtnContentHtml(label)` builds the icon+label markup shared by `attachLoadMoreRow`'s button and the plain `<a class="more-btn">` "View all" links `profile.js`/`shows.js` append when a preview row has more items than it shows (card-sized tile, not the small dot it used to be — sized and styled to look like one more slot in the row rather than a separate, oddly-proportioned control).

Adding a new page that lists movies/shows should reuse `buildCard`/`attachStandardActions`, not duplicate card-rendering logic.

**Card action layout:** the save/favorite/watched buttons live as an absolutely-positioned overlay on the poster image (`card.overlayActionsEl`), pinned to fixed corners via `.card-action-tr/-bl/-br` (eye=watched top-right, heart=favorite bottom-left, bookmark=save bottom-right) — not in the footer below the title. Lists/Bookmarks' list-removal button (`attachRemoveButton`) reuses the same overlay rather than a separate footer row, taking the one remaining unused corner (`.card-action-tl`), since it isn't part of `attachStandardActions` and only applies on list-management pages.

**Every card-shaped element derives its size from one set of CSS custom properties** (`--card-width`, `--card-poster-ratio`, `--card-info-height`, defined on `:root` in `style.css`) instead of hardcoding its own numbers — `.card`, `.media-grid`'s columns, and the Lists "add item"/"load more" tiles (`.add-item-card`, `.more-card`) all compute their size from these. This was a deliberate fix for a real bug: `.add-item-card`'s height used to be a hardcoded pixel value tuned only for one card size, so when `--card-width` needed to change between a desktop and mobile breakpoint (there's no longer a desktop layout at all — see the mobile-only note further down) it silently went out of sync and, combined with `.media-container`'s flex default `align-items: stretch`, stretched every real card in that row to match its oversized neighbor. `.media-container`/`.media-grid` now also set `align-items: flex-start`/`start` explicitly so a taller sibling can never do that again regardless of how its height is computed.

**Watched tracking has two different shapes on purpose.** Movies are a single boolean (`watched_movies` store). TV is tracked per episode (`watched_episodes`, one row per show/season/episode) because per-episode progress is the core feature — there's no cached progress counter; "X/Y watched" is always computed live by combining the local watched count with TMDB's `number_of_episodes`. `detail.js`'s season accordion lazy-loads episode lists per season and, when you mark an episode watched, offers a "catch up" prompt to bulk-mark every earlier unwatched episode across all prior seasons too.

**Bookmarks are still stored as a list under the hood** — the one `lists` row per profile with `isDefault: true`, auto-created when a profile's database is first opened — but is treated as a separate concept in the UI: `lists.js`'s `fetchLists()` filters out the default list, so it never appears on `lists.html`, and `bookmarks.html` is its own dedicated page (with movie/show items split into two separate `.media-container`s). It still shows up as a checkable option in the "Save to a list" popover (`media.js`'s `attachSaveButton`, which hits `GET /api/lists` directly and isn't filtered) since that's still how items get added to it. Don't add a parallel bookmarks store/API if extending this — the split is presentation-only.

**Ratings:** stored as an integer 1–10 (`ratings` store, keyed by `{mediaType}:{tmdbId}`), but only ever displayed as a 5-star half-increment widget on the detail page (`star value = rating / 2`). Cards elsewhere (Home/Bookmarks/Lists/Profile) do not show a rating control at all — that was deliberately removed in favor of detail-page-only rating.

**`detail.html`/`detail.js` is the single content page for both movies and shows**, distinguished by a `?type=movie|tv&id=<tmdbId>` query string — there's no separate movie-detail vs show-detail template. TV-specific sections (seasons/episodes) are simply hidden/skipped when `type=movie`. Cast cards link through to **`person.html?id=<tmdbId>`** (`person.js`). That page has a photo, department, birthday/age, birthplace, a clamped biography with a Show more/less toggle (shown only when the text is actually cut off; episode overviews in the season accordion use the same pattern), and a filmography grid from `/person/{id}/combined_credits` (cast+crew deduped, newest first, `FILMOGRAPHY_PAGE_SIZE` 8 per page) built with `buildCard`/`attachStandardActions`. Person results also appear in global search, both the typeahead and the full results page.

**The "standard item shape" has one definition: `public/scripts/standardItem.js`.** `{ tmdbId, mediaType, title, year, releaseDate, posterPath, voteAverage }` is what every page passes around for a movie/show. `toStandardItem(raw, mediaType?)` builds it from any TMDB movie/tv object. `mediaType` defaults to the raw object's `media_type`, which TMDB only sends on mixed-type endpoints (trending, multi-search, combined_credits), so single-type callers pass it explicitly. `unknownStandardItem()` is the failed-lookup placeholder, and `pickSummaryFields()` is the subset written onto watched/favorite rows. `localApi.js` (`summaryFromTmdbData`, recommendations), `media.js`, `detail.js` and every page script use these; don't add another mapping. This used to be four hand-synced copies.

**Unreleased-content gating** goes through the same file's `isUnreleased(dateStr, now?)`: a missing or future date means it can't be marked watched yet. Its users:
- `media.js`'s `attachWatchedButton` disables the watched toggle.
- `detail.js`'s `buildEpisodeCard` disables it and swaps in "Coming Soon" placeholders.
- `movies.js`'s Coming Soon row uses it as the `attachLoadMoreRow` `filterItem`, because TMDB's `/movie/upcoming` includes titles that have already released by fetch time.
- `localApi.js`'s new-episode check uses it to ignore unaired episodes.

Separately, `detail.js`'s season accordion disables (not just labels) a season's header button when `episode_count === 0`, so tapping a Coming Soon season can't get stuck on a permanent "Loading episodes…".

**Recommendations** (`localApi.js`'s `GET /api/recommendations/:mediaType` route) are seed-based, not a raw TMDB passthrough: it seeds from the profile's 5 most-recently-touched watched/list items, fetches TMDB's `/recommendations` for each seed, merges and ranks by match count then popularity, and excludes anything already watched/listed or a seed itself. The seeding/ranking (the expensive part — one TMDB request per seed) only depends on watched/list state as of when it first runs, so the ranked pool is cached in memory per `mediaType` for the rest of the page's session (`recommendationPoolCache`) rather than redone on every paginated request; a fresh page load always starts over. `?page=` slices `REC_PAGE_SIZE` (20) items at a time off that cached pool for `attachLoadMoreRow`. Powers the "Recommended" rows on `movies.html`/`shows.html`.

**"Keep Watching" and "Airing Soon" rely on a bounded new-episode heuristic**, not a webhook/polling system: `localApi.js`'s `computeNewEpisodeSeasons` only checks seasons at or above the profile's highest-watched season, comparing episode air dates against `lastWatchedAt`. This feeds the "new episode" dot on `shows.js`'s Keep Watching cards, the "New" labels in `detail.js`'s season accordion, and (via `GET /api/watched/shows/upcoming`) the Home page's "Airing Soon" row, which distinguishes a logged-out empty state from a logged-in-but-nothing-upcoming one via a 401 check.

Also: `movies.js`/`shows.js`'s "Popular" rows use `discover/movie|tv?with_origin_country=<region>` (region guessed from `navigator.language` via `media.js`'s `getUserRegion()`) to bias results toward the user's locale.

**This is a phone/tablet app, not a website — there is no desktop layout.** `#sidebar` is always a fixed bottom tab bar (icon-only, no text labels, no collapse/expand toggle); there's no `@media` breakpoint switching to a wider-screen layout, since one never renders at desktop widths. If you're touching sidebar/layout CSS, there's only ever the one definition to update, not a desktop version plus a mobile override.

**TMDB attribution** (per their API Terms of Use) lives on `profile-picker.html` — the bottom tab bar is only 60px tall, with no room for a logo and a sentence of credit text, so it isn't shown there at all.

## Testing

Run with `npm test` (`node --test tests/`, no framework, Node 18+). `tests/harness.js` loads the real `standardItem.js`/`localDb.js`/`localApi.js`/`profiles.js`/`backup.js`/`autoBackup.js`/`notifications.js` into a Node `vm` context that stands in for one browser page. It provides `fake-indexeddb` (the only dev dependency the tests need), an in-memory `localStorage`, and a fake TMDB server keyed by path, then drives the page through the shimmed `fetch('/api/...')` exactly like the app does. So the tests exercise the real route handlers, not copies of them. Each `createApp()` is a fresh page load, with a fresh DB and fresh module state. `put()`/`getAll()` read and write IndexedDB directly, to set up state the routes can't produce (e.g. a `watchedAt` in the past). `call(fnName, ...args)` calls any page-level function and returns a plain copy of the result. `createApp({ native: true })` makes `Capacitor.isNativePlatform()` true and installs in-memory fakes of the Filesystem and LocalNotifications plugins (returned as `filesystem`/`notifications`; options can make deletes or writes fail, or deny notification permission), so auto-backup and notification logic run exactly as on the phone.

Covered: lists, watched movies (including denormalize/backfill/limit), favorites, ratings validation, stats, the new-episode heuristic, upcoming, recommendations ranking/seeding/paging/cache, the detail cache (including `next_episode_to_air` expiry) and in-flight dedup, retries, adult filtering, passthrough auth, backup export (no key)/restore/legacy files, auto-backup scheduling/replacement/failed deletes/failed writes, notification scheduling/throttling/permission/disable, and TMDB key validation. Not covered: anything DOM-side (`media.js`, page scripts, the picker/profile UI wiring) and the real Capacitor plugins. Check those in a browser by serving `public/` statically (`.claude/launch.json` has an `npx serve` config), and on a phone for anything native.

Values created inside the vm context have that context's `Object.prototype`, so `assert.deepEqual` treats them as a different type. JSON round-trip them first (the tests' `plain()` helper). API responses are already parsed in the outer realm, so they're fine.

## Known gaps

- **No DOM/UI tests.** The test suite covers the data layer, backups and notification scheduling, but card rendering, page scripts and the native plugins themselves are only verified by hand.
- **No real background work.** Auto-backups and notification rescheduling only happen when the app is opened. Once scheduled, notifications fire on their own, but a show's following episode is only scheduled on a later app open.
- **Auto-backup can't delete files from a previous install** (Android scoped storage), so after a reinstall the user removes older `Documents/Watchlog` files by hand.
- **No release build setup.** `android/app/build.gradle` is still `versionCode 1`/`versionName "1.0"` with no release signing config; only debug APKs are produced.
- The old server-backed website's data (from before this repo's rebuild) has no migration path into a local profile's IndexedDB — it's a different storage shape entirely. The server-backed version itself is preserved in this repo's git history (before the local-first rebuild commit) and is also the current state of the separate [Movie-and-Show-tracker-Website](https://github.com/EasyBuster200/Movie-and-Show-tracker-Website) repo.
